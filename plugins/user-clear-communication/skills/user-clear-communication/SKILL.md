# User Clear Communication

## Основное правило

Пиши так, чтобы пользователь понял смысл без расшифровки внутреннего языка агента.

Важный ответ строится в таком порядке:

1. Смысл: что произошло на самом деле.
2. Решение: что теперь можно, нельзя или нужно сделать.
3. Польза: чем это помогает пользователю или проекту.
4. Доказательства: команды, файлы, числа, статусы и журналы.

Для микрозадач не добавляй тяжелую структуру. Одного ясного абзаца достаточно, если в нем есть смысл и следующий шаг.

## Перед Ответом

Проверь:

1. Что пользователь сейчас пытается решить.
2. Что изменилось после работы.
3. Что это значит для проекта.
4. Какой ближайший шаг или выбор нужен.
5. Какие детали нужны для доверия.
6. Какие внутренние термины надо заменить обычным языком.
7. Не потеряны ли важные факты ради краткости.

## Формат Чата

Обычный итог:

```markdown
**Вывод**
[Что произошло и что это значит.]

**Что изменилось**
- [Конкретное изменение.]
- [Конкретное изменение.]

**Следующий шаг**
[Один ближайший шаг или решение.]

**Проверка**
- [Что проверено и какой результат.]
```

Если ответ простой, не используй заголовки:

```text
Проверка нашла устаревший список документов. Это не ломает продукт, но мешает доверять отчету о готовности. Нужно обновить список и повторить проверку.
```

## Если Проверка Не Прошла

Не начинай с `FAIL`, пути к файлу или команды.

Порядок:

1. Что именно не прошло.
2. Насколько это опасно.
3. Почему это произошло простыми словами.
4. Что делать дальше.
5. Технические детали ниже.

Пример:

```text
Проверка не подтвердила готовность отчета. Главный список отстал от фактических файлов, поэтому отчету пока нельзя полностью доверять. Код продукта это не ломает. Следующий шаг — обновить список и повторить проверку.

Деталь: `.factory/specs` содержит 58 документов, а в списке указано 57.
```

## Если Пользователь Недоволен

Не защищайся списком проверок.

Порядок:

1. Проверь замечание пользователя.
2. Если замечание верное, признай его прямо.
3. Назови системную причину.
4. Предложи изменение процесса.
5. Согласуй или выполни ближайший шаг.

Пример:

```text
Да, проблема не в одном абзаце, а в том, как я перевел работу в отчет. Я слишком много доказывал факт выполнения и мало объяснял, что это меняет для проекта. Исправляю формат: сначала вывод и решение, потом проверки.
```

## Язык И Термины

Не смешивай языки в главном объяснении. Сначала дай русский смысл, затем технический термин в скобках или отдельной строкой, если он нужен для связи с кодом.

Плохо:

```text
Есть count drift в inventory.
```

Лучше:

```text
Главный список устарел и не совпадает с реальными файлами.

Техническая деталь: это `count drift` в `inventory`.
```

Не используй пустые управленческие фразы без фактов.

Плохо:

```text
Мы повысили прозрачность и управляемость процесса.
```

Лучше:

```text
Теперь перед началом изменения агент должен проверить, можно ли безопасно менять код этого проекта. Если проект не готов, агент останавливается и объясняет, что нужно проверить сначала.
```

## Локальный Словарь

Если в проекте часто встречается внутренний термин, держи перевод прямо в рабочем контексте или в проектном документе. Не заводи отдельный справочник без необходимости.

Минимальный формат:

```markdown
| Технический термин | Сначала сказать | Термин можно добавить ниже |
| --- | --- | --- |
| `count drift` | главный список устарел и не совпадает с реальными файлами | `count drift` |
| `guardrails` | правила, которые останавливают опасные действия | `guardrails` |
| `handoff` | короткая передача состояния следующей сессии | `handoff` |
```

## Контроль Перед Отправкой

Перепиши ответ, если:

- первый абзац непонятен без таблиц, команд и внутренних статусов;
- технические детали стоят раньше вывода;
- ответ начинается с `OK`, `FAIL`, пути к файлу или команды;
- есть смесь русского и английского в ключевом выводе;
- есть фраза вроде "стало лучше" без конкретного изменения;
- пользователь не сможет принять решение по верхней части ответа;
- доказательства заменяют вывод, а не подтверждают его.
