GOAL
▸Let an analyst take the numbers they see on the report page into a spreadsheet, without asking anyone for a database dump.
CONTEXT
  • Exists: the report page renders a filtered table server-side.
  • Foundation: the shared query builder from #003 (merged).
  • Who: an analyst, at the end of a weekly review.
CONSTRAINTS
  • The export follows the filters on screen, not the whole table.
  • No new background jobs — the file is produced in the request.
  • Rows are capped at 50 000; above that the user is told, not truncated.
USER STORIES
US-1As an analyst, I want to download what I see, so that I can work on it in a spreadsheet.
  • An export control is visible on the report page.
    Check: open the report with any filter set — expect an export control next to the filters.
  • The file holds exactly the filtered rows, in the on-screen column order.
    Check: filter to one week, export, open the file — expect the same rows and columns as on screen.
  • The download names the file after the report and the date.
    Check: export twice on different days — expect two differently named files.
US-2As an analyst, I want to be told when the export is too large, so that I narrow the filter instead of waiting.
  • Above the row cap the export is refused with a message naming the cap.
    Check: clear all filters on a large report — expect a message that names the limit and no download.
OUT OF SCOPE
  • Scheduled or emailed exports.
  • Any format other than CSV.
  • Exporting from the dashboard tiles.
MOCKUP

OPEN QUESTIONS → DECISIONS
Should the export follow the on-screen filters, or always cover the whole report?
Proposed: follow the filters — the analyst is exporting what they are already looking at.
Above the row cap: refuse with a message, or export the first rows?
Proposed: refuse and name the cap — a silently truncated file reads as complete.
